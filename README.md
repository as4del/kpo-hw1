# ВышКат: журнал приёмки

ДЗ1 по КПО. Консольное приложение на Java 25: приём транспорта после техосмотра,
учёт вещей, сводка энергопотребления, подбор техники для новичков и инвентарный список.
Все данные находятся в памяти и исчезают при завершении программы.

## Запуск

Нужен JDK 25. Gradle Wrapper включён; при первой сборке нужен интернет.

```bash
./gradlew --quiet --console=plain run
```

Windows: `gradlew.bat --quiet --console=plain run`.
В IntelliJ IDEA импортируйте Gradle-проект, выберите JDK 25 и запустите
`ru.hse.ledger.Launcher`. Ввод и вывод используют UTF-8.

Для запуска без Gradle после сборки:

```bash
./gradlew installDist
./build/install/vyshkat-ledger/bin/vyshkat-ledger
```

В Windows скрипт находится в `build\install\vyshkat-ledger\bin\vyshkat-ledger.bat`.
Команда `./gradlew distZip` создаёт архив приложения в `build/distributions/`.
Для передачи исходников нужны `src`, `config`, `gradle`, оба `gradlew`, оба файла
`*.gradle.kts`, `.gitignore` и README. Каталоги `build` и `.gradle` не нужны.

## Работа с программой

После запуска отображается справка. Команды вводятся по одной на строку;
регистр команд не имеет значения.

- `types` — показать доступные виды и их обозначения.
- `add scooter` — принять электросамокат.
- `add bike` — принять обычный велосипед.
- `add ebike` — принять электровелосипед.
- `add helmet` — поставить на баланс шлем.
- `add cabinet` — поставить на баланс зарядный шкаф.
- `summary` — количество транспорта, вещей, всех объектов и суточная энергия.
- `beginners` — принятый транспорт с простотой от 6 до 10 включительно.
- `inventory` — номера и названия всех объектов в порядке приёмки.
- `help` — справка; `exit` или `0` — выход.

После `add` программа последовательно спрашивает характеристики. Названия могут
содержать пробелы. Простота транспорта — целое число 1–10. Тормоза и колёса:
`да`/`нет` в любом регистре или `1`/`0`. Электрические устройства дополнительно
запрашивают расход в кВт·ч/сутки. Велосипед и шлем электричество не потребляют.
Зарядный шкаф участвует в общей энергии баланса наряду с транспортом.

Техосмотр проводится только для транспорта. Оба условия обязательны:
исправные тормоза и целые колёса. При отказе выводятся все найденные неисправности.
Объект не попадает в отчёты; его номер можно использовать после ремонта.
Вещи принимаются без техосмотра. Безопасность шлемов здесь отдельно не моделируется.

Номер и название обязательны; пробелы по краям удаляются. Номер уникален для
всего баланса, сравнивается с учётом регистра, ведущие нули сохраняются.
Дубликат не заменяет прежний объект; повторный техосмотр не вызывается.
Из-за последовательного ввода проверка дубликата выполняется после заполнения
характеристик, перед обращением к станции.

Расход — от 0 до 1 000 000, до трёх значащих дробных разрядов; разрешены точка
и запятая. Например, `0,125` и `1.2500` допустимы, `0.0001` отклоняется.
Это явно выбранные ограничения учебной модели: энергия хранится как `BigDecimal`
со шкалой 3 и складывается точно. Чрезмерно длинные числа и опасные показатели
степени отклоняются до преобразования в фиксированную шкалу или вывода.

Некорректное значение повторяет запрос текущего поля. Неизвестная команда
показывает подсказку; неизвестный вид не начинает ввод объекта. При конце потока
во время приёмки незавершённая запись отбрасывается, приложение завершается.

## Проверка сценария

```bash
./gradlew --quiet --console=plain run < src/test/resources/walkthrough.txt
```

Сценарий начинает с пустых отчётов, показывает каталог и добавляет все пять видов.
Также демонстрируются исправление неверного ввода, отказ техосмотра сразу по двум
причинам, повторная приёмка под освобождённым номером, дубликат, неизвестные вид
и команда, все отчёты и выход.

В конце: **4 транспорта, 2 вещи, всего 6 объектов; 2.400 кВт·ч/сутки**.
Новичкам доступны `SC-17`, `EB-09`, `RETRY-1`; велосипед `BI-04` с простотой 5
остаётся в инвентарном списке. Отказанный самокат не увеличивает расход.
Конец ввода и дополнительные границы проверены автоматическими тестами.

## Устройство и SOLID

Один Gradle-модуль. Spring Context собирает граф бизнес-зависимостей; Spring Boot,
база данных, HTTP и отдельный репозиторий для каждого типа здесь не требуются.

- [`domain`](src/main/java/ru/hse/ledger/domain) содержит неизменяемые объекты.
  `Inventoried` задаёт номер и название, `Powered` — энергию. `Asset` хранит общие
  поля, `Vehicle` добавляет простоту и состояние, `Equipment` выделяет вещи.
  `ElectricVehicle` объединяет хранение расхода для самоката и электровелосипеда.
- [`inspection`](src/main/java/ru/hse/ledger/inspection) содержит контракт
  `ServiceCenter`, результат `Inspection` и правило `SafetyInspection`.
- [`registry`](src/main/java/ru/hse/ledger/registry) содержит `AssetRegister` и
  `AdmissionDesk`. Реестр хранит единую коллекцию; приёмка проверяет номер,
  вызывает техосмотр и записывает только принятый объект. Метод записи реестра
  доступен лишь внутри пакета. Отдельная перегрузка приёмки вещей принимает
  `Equipment`, поэтому транспорт нельзя передать в неё в обход техосмотра.
- [`report`](src/main/java/ru/hse/ledger/report) строит сводку `FleetTotals`, список
  для новичков и инвентаризацию из снимков реестра. Возвращаемые списки неизменяемы.
- [`console`](src/main/java/ru/hse/ledger/console) отвечает за диалог. `TerminalInput`
  разбирает поля, `AssetCatalog` задаёт доступные виды и фабрики ввода,
  `ConsoleApplication` исполняет команды.
- [`Bootstrap`](src/main/java/ru/hse/ledger/Bootstrap.java) объявляет бины;
  [`Launcher`](src/main/java/ru/hse/ledger/Launcher.java) открывает контекст и
  подключает консоль к полученным сервисам. Модель от Spring не зависит.

**SRP:** хранение, решение техосмотра, приёмка, отчёты и ввод имеют разные причины
для изменения и разнесены по классам. Смена вида отчёта не меняет приёмку.

**OCP:** приёмка и отчёты работают с `Vehicle`, `Equipment` и `Powered`. Новый вид
наследует нужный базовый тип и подключается к каталогу. В бизнес-логике нет проверки
на `Scooter` или `Bicycle`; подключение нового электрического транспорта проверено
тестом `newElectricVehicleParticipatesInAllReportsWithoutSpecialCases`.

**LSP:** любой транспорт сохраняет контракт простоты 1–10 и состояния, любой
потребитель возвращает проверенный неотрицательный расход. Неисправный транспорт
можно создать: это корректная заявка на приёмку, решение о допуске принимает станция.

**ISP:** инвентаризация отделена от электрического потребления. У шлема и обычного
велосипеда нет фиктивного метода расхода; зарядный шкаф реализует оба контракта.

**DIP — наиболее явный принцип:** `AdmissionDesk` получает интерфейс `ServiceCenter`
в конструкторе. Выбор станции делает контейнер в `Bootstrap`; приёмка сама её
не создаёт. Тест меняет бин станции и наблюдает другой результат приёмки.

**Сознательно ограничен OCP:** `ConsoleApplication.execute` перечисляет команды
через `switch`, поэтому новая команда требует его изменения. Для этого небольшого
интерфейса отдельный диспетчер с системой регистрации команд усложнил бы код.
Каталог видов тоже заполняется явно, зато новый вид не требует изменения отчётов
или приёмки. `AssetRegister` остаётся конкретным классом: реализации для базы
данных пока нет, интерфейс с единственной реализацией не добавлен.

## Расширение

Новый транспорт: наследник `Vehicle` или `ElectricVehicle`, фабрика в
`AssetCatalog` и тесты. Учёт, фильтрация новичков и энергия продолжают работать.
Если у вида появятся особые требования безопасности, нужно расширить модель
состояния и правило станции либо внедрить другую реализацию `ServiceCenter`.

Сотрудник: отдельная модель и сервис, без наследования от `Asset`. Он не должен
попадать на баланс и увеличивать количество транспорта или вещей.

Склад: уникальные инструменты можно моделировать наследниками `Equipment`.
Остатки однотипных запчастей требуют отдельного учёта количества и движения,
а не множества искусственных уникальных номеров. Добавление такого модуля
не меняет текущие правила транспортной приёмки.

Для сохранения между запусками понадобится выделить контракт реестра из
`AssetRegister` и подключить постоянное хранилище через конфигурацию контейнера.
Приложение рассчитано на один последовательный консольный сеанс; многопоточную
приёмку с атомарной проверкой номера отдельно не реализует.

## Автоматические проверки

```bash
./gradlew clean check
```

Команда запускает JUnit 5, Checkstyle и проверяет покрытие JaCoCo **не ниже 60%**
по инструкциям для основного кода. Порог участвует в сборке и не игнорируется.
Используется собственный небольшой набор правил в `config/checkstyle.xml`:
именование, отсутствие неиспользуемых и звёздочных импортов, обязательные скобки,
длина строки 110, отсутствие табуляции и лишних операторов.

- [`AdmissionTest`](src/test/java/ru/hse/ledger/AdmissionTest.java) проверяет
  отказ без побочных эффектов, повторное использование номера, общую уникальность,
  точную сумму, границу 5/6 и расширение новым транспортом.
  `containerInjectsSubstituteAndItsDecisionIsFinal` регистрирует тестовую станцию
  как `@Primary`-эквивалент через `setPrimary(true)` в настоящем Spring-контексте:
  она принимает неисправный транспорт и отклоняет исправный, доказывая, что
  решение приходит именно от внедрённой зависимости.
- [`DomainTest`](src/test/java/ru/hse/ledger/DomainTest.java) проверяет все четыре
  сочетания состояния тормозов/колёс, ограничения полей, диапазон простоты,
  энергию и экстремальные показатели степени.
- [`ConsoleTest`](src/test/java/ru/hse/ledger/ConsoleTest.java) исполняет
  демонстрационный файл, проверяет ошибочные значения, завершение потока во время
  добавления и выход. Тесты используют потоки в памяти и не зависят от терминала.

Результаты: `build/reports/tests/test/index.html`.
Покрытие: `build/reports/jacoco/test/html/index.html`.
Стиль: `build/reports/checkstyle/main.html` и `test.html`.
